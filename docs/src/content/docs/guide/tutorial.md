This tutorial walks one configuration file through YewSeal's whole lifecycle: initialize a project, encrypt, commit and push, clone on another machine, and decrypt. Every output below comes from a real run — your keys and ciphertext values will differ.

:::note
YewSeal is config-driven. File mappings and recipient authorization are declared once in `.yewseal.toml`; command arguments only select among the registered files. If you already know SOPS, the "SOPS users" notes along the way call out the differences that matter.
:::

## Preparation

Install `yews` ([Installation](/guide/installation)), then set up a small Git project with a secret in it:

```bash
$ mkdir myapp && cd myapp && git init
```

Create a configuration file with a value you would never want in Git history:

```toml
# config.toml
db_url = "postgres://localhost:5432/app"
[server]
port = 8080
api_key = "hunter2"
```

This file should never be committed as plaintext — that is the problem YewSeal solves.

## Initialize the project

`yews init` scaffolds everything: an Age key pair, the project config, a `.gitignore` entry set, and a SOPS config. Run interactively, it asks which files to register; here we pass the mapping explicitly so the walkthrough reproduces exactly:

```bash
$ yews init --input config.toml --output config.enc.toml --format toml
Initialized 1 file mapping: .yewseal.toml, .age/keys.txt, .gitignore, .sops.yaml
```

Four things were created. Let's look at each.

### The private key: `.age/keys.txt`

```text
# created: 2026-09-12T14:05:21Z
# public key: age1rczdrfjqq8h9e8hpax33j8smdcvgjzspxzhy4afp2fqx8d4hxqjq89sv49
AGE-SECRET-KEY-1QYP...   (private key elided)
```

This Age identity is the project owner's. The **public key** (`age1...`) may be shared freely; the **private key** (`AGE-SECRET-KEY-...`) decrypts and must never leave this machine. YewSeal deliberately does not sync private keys anywhere — how you back them up or hand them to CI is your choice ([External private key sources](/guide/private-keys)).

### The project config: `.yewseal.toml`

```toml
[encryption]
[[encryption.files]]
plaintext = 'config.toml'
encrypted = 'config.enc.toml'
format = 'toml'
recipients = ['owner']

[recipients]
defaults = ['owner']

[recipients.registry]
owner = 'age1rczdrfjqq8h9e8hpax33j8smdcvgjzspxzhy4afp2fqx8d4hxqjq89sv49'
```

Three declarations live here:

- `[[encryption.files]]` — the mapping between one plaintext file and one encrypted file. This pair is now the only thing `encrypt` and `decrypt` will ever touch.
- `[recipients.registry]` — public keys under reviewable aliases. `owner` is the public key from your `.age/keys.txt`.
- `recipients` on a file (or `recipients.defaults`) — who a file is encrypted **to**. Aliases only, never raw keys.

:::note[SOPS users]
There is no `--age` flag and no `SOPS_AGE_RECIPIENTS`. YewSeal resolves encryption recipients solely from this registry — that is what keeps authorization reviewable in code review. See [Interop with SOPS](/guide/sops).
:::

### The managed SOPS config: `.sops.yaml`

```yaml
# Generated by YewSeal. DO NOT EDIT.
# This file is fully managed and will be overwritten by init/sync/encrypt.
creation_rules:
    - path_regex: ^config\.enc\.toml$
      age: age1rczdrfjqq8h9e8hpax33j8smdcvgjzspxzhy4afp2fqx8d4hxqjq89sv49
```

YewSeal embeds the SOPS engine, so this file is not needed for `yews` itself — `init` and `encrypt` keep it in sync so the standalone `sops` CLI stays usable on the same files.

### The `.gitignore`

```gitignore
# YewSeal - Decrypted configuration files
config.toml

# YewSeal - Age private keys
.age/keys.txt
```

The plaintext and the private key are excluded; the encrypted counterpart will be committed instead.

## Preview the selection

Before writing anything, `yews plan` reports what the config currently resolves to — mappings, formats, and who each file is authorized for:

```bash
$ yews plan
Loaded 1 config file
Command plan
Scope .
Selected 1 file pair

Plaintext    P.Source             Encrypted        E.Source             Format  F.Source              Aliases  Recipients                                                      Authorization             Registry Sources     Selected By
config.toml  .yewseal.toml exact  config.enc.toml  .yewseal.toml exact  toml    .yewseal.toml format  owner    age1rczdrfjqq8h9e8hpax33j8smdcvgjzspxzhy4afp2fqx8d4hxqjq89sv49  .yewseal.toml recipients  owner=.yewseal.toml  current-directory
```

Every `Source` column answers "where did this come from?" — the mapping is exact from `.yewseal.toml`, the format is declared on the file pair, and the recipient set came from the file's `recipients`. Nothing is written; run `plan` after any config edit to catch unknown aliases or empty authorization sets before they bite during encryption. It reads no private keys and is not a dry run.

## Encrypt

```bash
$ yews encrypt
Summary (encrypted): 1 succeeded, 0 skipped, 0 failed (1 selected)
```

Take a look at what was written:

```toml
# config.enc.toml (excerpt)
db_url = 'ENC[AES256_GCM,data:HeYh4yNERUHlfA49HkOFg+9KWOZNvWl3RLkDtBA=,iv:Idme6dGVpGLRaO76x4iuTdn1Cbs3Ov4V59bTfxLbp2E=,tag:1PWqXzVACE3mF6ALGkcplw==,type:str]'

[server]
port = 'ENC[AES256_GCM,data:qB+9Vw==,iv:OkS7ZlpFV1+oyFW7PR2sKHtkYI44KauOtrV45Irwmmg=,tag:9VNXPxGhfDEfQxiAccH3Uw==,type:int64]'
api_key = 'ENC[AES256_GCM,data:CxE3f6x03A==,iv:OFu791DaIIQte3xV4H9Evg1ynpw1ZEzi6rJLuc/P61Y=,tag:we5g1hBK5dqIu0d8w3a3lw==,type:str]'
```

Values are encrypted individually; the structure — keys, tables, ordering — stays visible, so diffs stay meaningful in code review. Each value carries its own authenticated encryption. YAML, JSON, ENV, INI, and binary files go through the same engine natively.

## Commit and push

Commit the ciphertext together with the config:

```bash
$ git add .yewseal.toml .sops.yaml .gitignore config.enc.toml
$ git commit -m "Add encrypted config"
$ git push
```

`config.toml` and `.age/keys.txt` are not offered to Git at all — the generated `.gitignore` already excludes them. What lands in the repository is the encrypted file plus the reviewable declaration of who may read it.

## Clone on another machine

This is the payoff. On a laptop (or in CI), clone the repository:

```bash
$ git clone git@github.com:you/myapp.git && cd myapp
$ ls
config.enc.toml
```

Only the ciphertext came along — exactly as intended. Ask YewSeal to restore the plaintext:

```bash
$ yews decrypt
Error: no Age key found. Options: --key-file, YEWSEAL_AGE_IDENTITIES, SOPS_AGE_KEY, SOPS_AGE_KEY_FILE, SOPS_AGE_KEY_CMD, or .age/keys.txt
```

Right — this machine holds no identity yet. Provide one of yours (the [resolution order](/guide/configuration#reading-private-keys) tries the flag, then the environment variables, then `.age/keys.txt`). Copying the owner key file in via your usual secret channel:

```bash
$ mkdir -p .age && cp ~/backups/myapp-age-key.txt .age/keys.txt
```

```bash
$ yews decrypt
Summary (decrypted): 1 succeeded, 0 skipped, 0 failed (1 selected)

$ cat config.toml
db_url = 'postgres://localhost:5432/app'

[server]
port = 8080
api_key = 'hunter2'
```

The values are back. One detail worth noticing: the quotes changed from `"..."` to `'...'`. Decrypted files are re-serialized by the format's store, so whitespace and quoting may differ from the original even though the content is identical.

`decrypt` is careful with existing files: if `config.toml` already exists and differs from the decrypted result, the command refuses to overwrite and tells you to pass `--force`. A stale plaintext never gets silently clobbered.

## The daily edit loop

Two equivalent ways to change a secret.

**Edit the plaintext, then re-encrypt.** This fits a normal editor workflow and lets you review before committing:

```bash
# change the port in config.toml, then:
$ yews diff config.toml
--- config.toml
+++ config.enc.toml (decrypted)
@@
 db_url = 'postgres://localhost:5432/app'

 [server]
-port = 9090
+port = 8080
 api_key = 'hunter2'

$ yews encrypt config.toml
Summary (encrypted): 1 succeeded, 0 skipped, 0 failed (1 selected)
```

`diff` compares the plaintext with the decrypted ciphertext — showing differences is never an error, so it works purely as a preview. Its body goes to stdout, summaries and warnings to stderr, which keeps it pipeable.

**Edit the ciphertext directly.** `edit` decrypts into a temporary file, opens your editor (`VISUAL`, then `EDITOR`), and re-encrypts on save. Your plaintext tree stays untouched:

```bash
$ VISUAL="code --wait" yews edit -f config.enc.toml
Updated config.enc.toml
```

For a quick peek without touching disk at all, `view` prints the decrypted file to stdout:

```bash
$ yews view config.enc.toml
$ yews view config.enc.json | jq '.database'
```

After either path, commit the new ciphertext — the plaintext is, as always, ignored:

```bash
$ git add config.enc.toml && git commit -m "Rotate api_key"
```

When you are done with the plaintext, remove it with a proven-recoverable cleanup instead of hunting files by hand:

```bash
# matching plaintext is removed; differences prompt with No as the safe default
$ yews clean
Plaintext differs from encrypted content: config.toml
Hint: run yews diff -- 'config.toml' to view the diff.
Delete the local plaintext anyway? [y/N]: n
RETAINED config.toml: plaintext differs from encrypted content
Summary (cleaned): 0 removed, 0 already absent, 1 retained, 0 failed (1 selected)

# done for the day: keep every unsaved difference, no prompts at all
$ yews clean --skip-different
```

If you saved your edits with `encrypt` first, `clean` removes the plaintext without asking. See [Cleaning local plaintext](/guide/plaintext-cleanup) for the verification rules, exit codes, and the irreversible `--remove-different`.
